# 백업 순환과 탈퇴 자동 확인 — 2026-09-14

운영자 결정: 전체 백업은 매주 만들고, 28일이 지난 백업은 삭제한다. 서버 로그도 28일까지만 보관한다. 탈퇴의 저장소별 확인은 서버가 자동으로 하고, 확인되지 않은 항목만 담당자가 처리한다.

## 백업 순환

| 항목 | 내용 |
| --- | --- |
| 스크립트 | 저장소 `deploy/backup_rotation.py`, 서버 `/app/backend/backup_rotation.py` |
| 일정 | `/etc/cron.d/dflh-backup-rotation`: 매주 일요일 04:10 전체 백업, 매일 04:40 정리 |
| 백업 위치 | `/app/backups/weekly-<UTC시각>/`: DB 덤프, 업로드 압축 2개, 체크섬 |
| 보관 | 생성 후 28일. 가장 최근 백업 하나는 백업이 실패해도 지우지 않는다 |
| 배포 백업 | `/app/releases/*/backup/`의 DB 덤프·업로드 압축·체크섬도 28일 후 삭제. 앱 복구용 스냅숏은 유지 |
| 기타 | `/root/db-backups`의 수동 덤프, 28일이 지난 웹 서버 순환 로그도 삭제 |
| 상태 파일 | `/app/backend/backup-rotation-status.json`: 날짜와 건수만 기록. 백엔드가 자동 확인에 읽는다 |
| 실행 기록 | `/var/log/dflh-backup-rotation.log` |

DB 덤프는 `--single-transaction`으로 떠서 운영 중 쓰기를 막지 않는다. 맥 등 서버 밖에 운영 DB 사본을 두지 않는다. 필요하면 사용 후 바로 지운다.

## 로그 보관

- 서버 저널: `/etc/systemd/journald.conf.d/dflh-retention.conf`의 `MaxRetentionSec=28day`.
- 웹 서버 로그: `/etc/logrotate.d/httpd`에 `maxage 28`. 순환되지 않고 남은 옛 로그는 정리 스크립트가 지운다.
- 결제 감사 로그(`/var/logs/pg`)는 회계 보존 대상이라 이 규칙에서 제외한다.

## 탈퇴 자동 확인

`ACCOUNT_ERASURE_EXTERNAL_MODE=internal`이면 서버가 DB 삭제와 파일 삭제 뒤 네 항목을 스스로 확인한다. 증거가 있을 때만 완료로 기록하고, 아니면 확인 대기로 남겨 관리자 화면에서 담당자가 처리한다.

| 항목 | 자동 완료 조건 |
| --- | --- |
| 백업 | 상태 파일이 36시간 이내 갱신, 최근 주간 백업이 8일 이내, 가장 오래된 백업이 29일 이내 |
| 과거 파일 | 앱이 관리하는 파일을 모두 지웠고 외부 파일 주소가 0건 |
| 간접 식별자 | 로그인·이메일·전화·소셜 식별값으로 운영 DB의 모든 문자열 칸을 검색해 0건 |
| 외부 서비스·로그 | Sentry 전체 프로젝트 90일 0건, 저널과 웹 서버 로그가 28일 순환 설정 |

같은 이메일을 쓰는 다른 계정처럼 자동으로 판단할 수 없는 경우는 담당자에게 넘긴다.

## 백업 복원 시 재삭제

탈퇴를 완료하면 회원 번호를 `ALUMNI_ERASURE_RESTORE_GUARD`에 35일 동안 남긴다. 28일 보관과 주간 간격을 더한 기간이며, 탈퇴 작업이 매번 만료된 기록을 지운다.

백업을 복원했다면 서비스를 열기 전에 반드시 실행한다.

```sh
cd /app/backend
./erasure-restore-reapply            # 되살아난 탈퇴 회원 수만 확인한다
./erasure-restore-reapply -apply     # 되살아난 회원을 같은 규칙으로 다시 지운다
```

기부 기록이 되살아난 회원은 보존 결정이 필요해 멈춘다. 이 경우 담당자가 기부 보존 절차를 먼저 처리한다. 복원 백업에 들어 있던 탈퇴 요청의 상태는 관리자 화면에서 다시 확인한다.
