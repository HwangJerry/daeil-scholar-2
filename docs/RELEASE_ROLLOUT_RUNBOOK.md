## 수정한 항목

- 자동 파일 큐 생성 전에 소유권 근거와 다른 회원·게시글의 참조를 확인한다. 확인되지 않은 파일은 보류한다.
- `/files`, `/upload`, `/old/upload`와 같은 사이트의 절대 URL을 같은 저장 경로로 비교한다.
- 실제 파일 삭제 직전에도 DB의 남은 참조와 자동 처리 상태를 잠금 안에서 다시 확인한다. 이후 큐 처리를 확인한다.
- 외부 프로필 URL은 로컬 파일 큐에 넣지 않는다. 외부 파일 주소는 암호화된 외부 처리 자료에 남으며, 외부 저장소 검증을 생략하거나 완료로 간주하지 않는다.
- 신규 접수, 자동 탈퇴 워커, 보관 만료 작업은 별도 설정으로 활성화한다. 기본값은 모두 중지다.
- 활성화 상태에서는 암호화 키·저장소 경로·외부 처리 방식을 검사한다. 접수 중지 시 503과 문의 창구를 안내하고 계정 상태·세션은 변경하지 않는다.
- 지정 테스트 회원만 접수·자동 처리할 수 있다. 테스트 단계에서는 다른 자료의 보관 만료 작업도 중지한다.
- 관리자는 외부 확인용 정보의 만료 시각과 파일 소유권/공유 참조 보류 사유를 볼 수 있다. 기존 10일 기한을 무제한 연장하지 않았다.

## 준비와 배포는 별도 명령

`deploy.sh`는 이제 미리 검증한 묶음만 배포한다. 기존 명령만 입력하면 준비 방법을 안내하고 종료하며 서버에는 접속하지 않는다.
`APPLY_MIGRATIONS=1`, `SKIP_ENV_CHECK`, `SKIP_MIGRATION_CHECK` 우회는 사용하지 않는다.

```sh
# 로컬 작업만 수행한다. 검토한 변경을 커밋한 뒤 실행한다.
./deploy.sh --prepare-only --patch-mode=false --output=/절대경로/새후보

# 실제 운영 실행: 현재 승인·실행하지 않은 단계다.
./deploy.sh daeil-prod --bundle=/절대경로/새후보 --apply-migrations
```

`--only=backend,frontend,admin` 중 원하는 구성요소를 준비할 때 선택할 수 있다.
웹만 배포할 때에도 해당 후보가 요구하는 063 스키마가 이미 적용돼 있어야 한다.
묶음은 별도 Git checkout에서 빌드한다. 공유 node_modules에 npm ci를 수행하지 않는다.
배포 시 다시 빌드하지 않는다. 서버/backfill의 clean commit 정보, 전체 파일 목록과 SHA-256을 검증한다.
서비스 비밀 값과 `.service` 파일, 전체 소스 checkout은 묶음에 넣지 않는다.
Apache 설정과 실제 업로드 대상인 PHP shim 3개는 묶음 및 복구 대상에 모두 포함한다.

## 운영 설정 사전 준비

아래 값은 향후 승인된 운영 설정 적용 단계에서 준비한다. 실제 비밀 키는 Git·문서·배포 묶음에 기록하지 않는다.

| 설정 | 확인할 내용 |
|---|---|
| ACCOUNT_ERASURE_CONTEXT_KEY | 별도 비공개 32바이트 hex 키 |
| DONATION_ARCHIVE_KEY | context 키와 다른 비공개 32바이트 hex 키 |
| ACCOUNT_ERASURE_LEGACY_ROOT | 확인한 물리 경로 `/var/www/html/upload` |
| UPLOAD_BASE_PATH | 실제 신규 업로드 경로와 디렉터리 권한 |
| ACCOUNT_ERASURE_EXTERNAL_MODE | `manual`: 기존 관리자 증빙 처리. `http`: 실제 연결된 외부 처리 API |
| ACCOUNT_ERASURE_EXTERNAL_URL / TOKEN | `http`인 경우 HTTPS 주소·토큰·처리 계약 검증 필요 |
| SENTRY_IOS_PROJECT / SENTRY_ANDROID_PROJECT | `daeil-ios-release` / `daeil-android-release`; 기존 토큰 접근 권한도 확인 |
| 기부 거래별 보존 결정·영수증 업무 | 앞서 정한 근거와 원본 연락처 확보 여부를 담당자가 확인. 빈 값을 승인으로 간주하지 않음 |

기존 JWT/Kakao/SMTP/PG 등 필수 환경 설정 검사도 유지했다.
새 바이너리의 `--check-release-config`는 DB에 연결하거나 작업을 시작하지 않고 설정을 검사하는 용도다.
외부 처리의 `manual`은 앱 DB/파일 삭제를 자동화하면서 외부 증빙은 기존 관리자 절차로 확인한다는 의미다.
완전 자동 외부 연동이 구현·검증됐다는 뜻이 아니다. `http`에는 더미 완료 응답을 사용하지 않는다.

## 실제 배포의 실행 순서와 중단 시간

1. 묶음을 전송하고 서버에서도 파일 목록·해시·기존 migration 해시·새 설정·복구 공간을 검사한다.
2. 기존 앱/설정/PHP shim 사본을 확보한다.
3. **Apache 및 백엔드를 중지한다. 이 구간에는 웹·레거시 PHP·API 접속이 일시 중단된다.**
4. DB 전체 dump와 두 업로드 루트의 압축 사본을 비공개 디렉터리에 저장한다. dump의 압축 무결성과 비어 있지 않음을 확인하고 자료 해시를 기록한다.
5. 승인한 미적용 migration만 순서대로 실행한다. 현재 관측 기준은 055–063 9개이며 매번 재확인한다.
6. 세 탈퇴/만료 기능을 중지하는 rollout 환경 파일을 적용하고 고정된 백엔드 파일을 교체한다.
7. API 및 DB 건강 상태, 실제 실행 바이너리의 해시, 중지 설정의 실제 적용 여부를 확인한다.
8. 웹·Apache·PHP shim을 교체한다. 이전 해시 웹 청크를 보존하고 index를 마지막에 교체한다.
9. Apache를 시작하고 공개 API 건강 상태까지 검증한다. 결과는 `DEPLOYED_ERASURE_PAUSED`로 남는다.

복구 자료는 `/app/releases/<release-id>/backup/`에 생성한다. 아직 운영에 생성한 자료는 아니다.
이는 새 상시 백업 서비스 도입이 아니라 배포 변경 직전의 제한된 복구 자료다.
이미 확보했던 애플리케이션 사본과 새 절차가 향후 만드는 DB/업로드 사본을 혼동하지 않는다.

실패하면 애플리케이션 파일을 원복하고 자동 삭제를 중지한 상태로 서비스를 다시 시작한다.
**DB 스키마는 자동으로 되돌리지 않는다.** 058 중간 실패는 적용 이력과 테이블 엔진을 확인한 뒤 재개해야 한다.
현재 변경은 부가 테이블 생성/엔진 전환이며, 자동 DB 복원으로 새 기록을 덮어쓰지 않도록 했다.
파일 원복 자체가 실패하거나 서버 연결이 끊기면 담당자가 복구 자료를 확인해야 한다.

## 운영 탈퇴 검증과 활성화

배포와 별도로, 사용자에게 승인받은 일회용 계정으로 검증한다. 기존 회원/기부/과거 로그 정리 결재를 대신하지 않는다.
서버에서 결과가 확인된 release-id를 사용한다.

```sh
# 해당 회원의 탈퇴 접수·자동 작업만 허용. 보관 만료 정리는 계속 중지.
./deploy.sh daeil-prod --release-id=<release-id> --activate-test-user=<일회용회원번호>

# 테스트 계정의 실제 탈퇴·소셜 철회·파일·기부 보존·외부 증빙까지 확인하고 별도 승인 후 실행.
./deploy.sh daeil-prod --release-id=<release-id> --activate-all-users

# 보관 만료 작업만 별도 활성화. 테스트 계정 모드에서는 거부된다.
# 현재 단계에서는 실행하지 않는다.
./deploy.sh daeil-prod --release-id=<release-id> --activate-retention

# 보관 만료 작업만 중지하고 현재 탈퇴 활성화 범위는 유지한다.
./deploy.sh daeil-prod --release-id=<release-id> --pause-retention

# 신규 접수와 자동 탈퇴/보관 만료 작업을 모두 중지.
./deploy.sh daeil-prod --release-id=<release-id> --pause-erasure
```

활성화 명령은 설정 검사 후 백엔드를 재시작하고 실제 적용된 설정을 확인한다.
배포·활성화·중지는 서버 공통 파일 잠금으로 직렬화한다. 다른 실행이 있으면 새 명령은 오류로 종료하며, 기존 실행 종료 후 재시도한다.
중지 명령은 백엔드/DB가 비정상이어도 설정을 끌 수 있도록 기존 프로세스 환경과 배포 해시 검증에 의존하지 않는다.
백엔드를 멈춘 뒤 비활성 설정을 원자적으로 기록하고 다시 시작해 실제 설정을 검사한다.
중지 검증 실패 시 백엔드는 중지 상태로 둔다. 활성화 실패도 설정을 끄고 백엔드를 중지하므로, 원인 확인 후 서비스를 복구해야 한다.
OS의 서비스 중지 자체가 실패하면 안전한 중지가 확인된 것으로 취급하지 않는다. 비활성 설정 기록을 시도한 뒤 오류를 보고한다.
중지 성공은 DB 건강 상태 복구를 의미하지 않는다. API 건강 상태는 별도로 확인한다.
이 동작에는 짧은 API 중단이 있으며, 복구 실패 시 담당자의 서비스 복구가 필요하다.

중지 명령은 이미 삭제한 자료를 복원하거나 기존 소셜 철회 요청을 취소하는 기능이 아니다.
전체 활성화 후의 삭제는 앱 파일 원복만으로 되돌릴 수 없다.

## 남아 있는 운영 검증 범위

- 실제 운영 설정 주입과 접근 권한 확인, 일회용 계정 승인, 운영 배포와 단계별 탈퇴 검증.
- 058의 운영 데이터/자원 조건에서의 소요 시간, 실제 복원 리허설과 업무 중단 시간 합의.
- 외부 확인 및 영수증 업무가 10일에 근접하면 담당자가 만료 전에 증빙을 처리해야 한다.
  만료된 경우 원본/외부 저장소별 증거를 수동 확인하며, 증거 없이 완료로 바꾸지 않는다.
- 타인 파일 참조 검사는 대상 테이블 범위를 잠근다. 잠금이 짧다고 보장할 수 없다. 운영 규모에서 지연을 관찰하고 문제가 있으면 자동 처리를 중지한다.

기존 `7fb7088`, `d34b19f` 배포 묶음은 결함 재현 당시의 검토 자료로 계속 보류한다. 새 후보를 사용해야 한다.

현재 배포 도구는 `REVIEW_STATUS.json` 상태가 `HOLD`로 시작하는 묶음을 전송 전에 거부한다.
이전 묶음에 들어 있는 이전 도구를 직접 실행하면 이 보호가 없으므로 보류된 묶음의 스크립트는 실행하지 않는다.


## 독립 검토 후 보완 후보

- 063은 기부 보존 결정을 검토 당시 원본과 연결하는 지문을 추가한다. 기존 기부 원본과
  보존 결정 행을 삭제하지 않는다. 지문 없는 기존 결정은 재검토 전 자동 삭제에 사용할 수 없다.
- 기부 수정과 기존 결정 무효화는 같은 트랜잭션에서 처리하고, 실제 삭제 직전에도 검토한
  원본과 현재 자료가 일치하는지 검사한다.
- 배너 이미지도 공유 파일 참조 검사에 포함한다. URL 자체의 HTML 엔티티를 임의 해제하지 않는다.
- iOS 탈퇴 재시도 수정은 서버 배포에 포함되지 않는다. 해당 iOS 수정 빌드도 별도로 검증·제출해야 한다.
- 독립 검토에서 문제를 재현한 `c0f5d96` 묶음은 보류를 유지하고 수정 후 새 후보를 사용한다.

  집계 존재는 내용의 정확성까지 보증하지 않는다. 과거 원본 삭제 후 통계를 재산출할 수는 없다.
- 차단 쪽지 정리는 기존의 수신자 비노출·차단 사유·만료 시각 조건과 100건 제한을 유지한다.
  삭제된 쪽지 본문 복원이나 분쟁 증빙 보존을 보증하지 않는다.
- 신규 보관 만료 작업의 완료된 account erasure 상태 정리에도 배치 제한을 적용한다.
  부모 접수 삭제에 따른 FK 하위 행 삭제는 부모 100건보다 많을 수 있으므로 활성화 전 규모를 확인한다.
- 전체 회원 탈퇴 활성화 명령은 보관 만료를 항상 끈다. 보관 만료 명령은 현재 탈퇴 범위를 유지한다.
  `--pause-erasure`는 비상 중지로서 두 기능을 모두 끈다.

## 일회용 계정 검증 준비 — 아직 운영 실행하지 않음

1. 운영자가 테스트 계정을 지정하고, 일반 회원과 구분되는 회원번호를 확인한다.
2. 해당 계정에 실제 기부·회계 기록이나 타인 소유 파일이 없는지 확인한다.
3. 격리된 로컬 합성 계정 테스트 통과 후 해당 회원번호에만 접수/워커를 활성화한다.
4. 계정 탈퇴 접수, 세션 무효화, 본인 자료 처리, 공유 파일 보호, 외부 공급자 증빙을 확인한다.
5. 완료 여부와 관계없이 검증 종료 후 비상 중지 명령으로 모든 신규 삭제 기능을 끈다.
6. 결과 검토 없이 전체 회원 또는 보관 만료 작업으로 확대하지 않는다.
