# iOS 출시를 위한 계정 삭제 마무리 계획

2026-09-07. 구현 계획이며, 아래 신규 작업이 구현·배포되었다는 의미가 아니다.

## 목표와 확정 사실

앱에서 탈퇴를 요청하면 계정·연결된 개인정보를 실제로 삭제하고, 필요한 기부 증빙만 보존한다. 기존 관리자 수동 전환·재개 기능은 유지한다. 새로운 별도 수동 시스템은 만들지 않는다.

- 회계연도 종료일: 12월 31일.
- 기부금 영수증: 해피나눔 디지털 발급 및 시스템 원본 보관.
- Sentry: 미국 저장, 체험 후 무료 요금제 사용 예정. 기존 테스트 프로젝트 삭제와 출시용 프로젝트 교체 완료.
- iOS Sentry 개인정보 최소화, 앱 DB·파일 삭제, 최소 기부 증빙 암호화·만료 삭제, 접수증·관리자 수동 기능은 구현되어 있다.
- 폰트와 개인정보처리방침은 수정되어 있다. 운영 배포·새 서명 출시 빌드 검증은 별도다.

## 0. 저장소 실사와 적용 기준 확정

우선 확인할 대상은 운영 스키마, 업로드 경로, 로그, 가비아 스냅샷/자동 백업, 별도 SQL 덤프·수동 백업, 해피나눔 원본과 가져오기 파일이다. 내용 전체를 복사하지 않고 설정·경로·보관 규칙·소유 관계부터 확인한다.

산출물은 저장소별 데이터 항목, 삭제 수단, 보관 종료 기준, 접근 담당자, 확인 증거를 담은 목록이다. 파일 소유 이력이 없는 경우 자동 삭제 가능한 자료와 운영자가 확인할 자료를 구분한다. 실행 중인 정기 결제·구형 빌링키가 있는지도 확인한다.

가비아 백업·해피나눔 원본 보존 설정 확인 담당자는 황제철로 확정했다. 실제 설정과 현재 연결로 확인할 수 없는 관리 화면 접근 방법은 확인이 남았다. 이미 제공한 회계연도·발급 시스템을 다시 묻지 않는다.

## 1. 자동 삭제 흐름과 완료 판정 보완

**문제:** 현재 `AutomaticErasureService`는 외부 처리 증거를 받은 뒤에야 DB 삭제를 시작한다. 외부 연동이 없으면 계정 비활성화 상태에서 개인정보 삭제도 대기한다. 외부 시스템마다 다른 상태를 단일 성공 응답으로 표현하고 있다.

**구현:**

- 저장소별 작업·상태·재시도·검증 근거를 영속 저장한다. 상태는 대기, 처리 중, 완료, 해당 없음, 수동 확인, 실패를 구분한다. 해당 없음은 실제 조사 근거가 있어야 한다.
- 삭제에 필요한 최소 외부 식별정보와 파일 참조를 보호된 작업 레코드에 먼저 확보한다. 개인정보 원문은 일반 로그에 남기지 않고 암호화·접근 제한·만료 정책을 적용한다.
- 기부 분류와 필요한 소셜 철회를 확인한 뒤 운영 DB·현재 파일 삭제를 진행한다. 외부 처리가 오래 걸린다는 이유로 다른 개인정보까지 유지하지 않도록 단계를 분리한다.
- 기존 `EXTERNAL_EVIDENCE` 선행 조건, 재검증 쿼리, 자동 완료 조건을 함께 변경한다. 서비스만 바꾸고 저장소의 기존 선행 조건을 남기지 않는다.
- 외부 삭제 요청에도 대상별로 필요한 최소 정보만 전달한다. 백업·로컬 파일 정리는 가능한 경우 기존 서버의 작업으로 구현하고, 별도 HTTPS 서비스는 실제로 필요할 때만 사용한다.
- 모든 필수 작업이 검증된 뒤 최종 완료 처리한다. 일부만 끝난 경우 앱 데이터 삭제와 남은 외부 처리 상태를 구분해 안내한다. 대기 중인 것을 완료로 바꾸지 않는다.
- 이전 요청을 중복 삭제하지 않는 마이그레이션과 단계별 재개 경로를 제공한다. MariaDB 10.1 및 기존 InnoDB 전환 조건을 유지한다.

**완료 기준:** 외부 서비스가 중단되어도 삭제 가능한 앱 데이터는 제거되며, 작업 재시작·동시 탈퇴·수동 전환 후에도 중복 보존이나 잘못된 완료가 없다.

## 2. 백업·복원·과거 파일 처리 연결

**구현:**

- 확인된 관리 경로·저장소만 대상으로 삭제 작업을 연결한다. 경로 이탈·심볼릭 링크·다른 회원 파일은 자동 삭제하지 않는다.
- 과거 사진·명함·첨부파일의 소유 관계를 복원할 수 있으면 소급 등록한다. 추정만 가능한 파일은 기존 관리자 확인 절차로 넘긴다.
- 백업에서 선택 삭제가 가능한 경우 실제 삭제 후 확인한다. 불가능한 스냅샷은 접근 제한, 검증된 만료일, 실제 만료 확인을 추적한다. 임의로 모든 백업에 동일한 기간을 적용하지 않는다.
- 운영 DB 백업과 독립적으로 유지되는 최소 삭제 이력을 사용해, 복원 직후 서비스 공개 전에 탈퇴 데이터 삭제를 재적용한다. 이 이력도 개인정보일 수 있으므로 필요한 복원 가능 기간과 목적으로 보관을 제한한다.
- 로그의 불필요한 개인정보 기록을 차단하고 기존 로그에는 실제 저장 방식에 맞는 정리·만료 작업을 연결한다.
- 기존 백업의 정리, 새 백업의 보존·만료 작업, 복원 시 삭제 재적용을 모두 운영 절차에 포함한다.

**완료 기준:** 테스트 계정을 삭제한 뒤 이전 백업을 격리 환경에 복원해도 서비스 재개 전에 계정·파일이 다시 제거된다. 만료 예정과 실제 삭제 완료가 구분된다.

## 3. 기부 원본·앱 사본 분류와 재유입 방지

**기준 확정:** 해피나눔 원본이 보존 의무를 충족하는지와 앱 사본을 별도로 보관해야 하는지를 확인한다. 디지털 발급을 홈택스 법정 예외로 간주하거나 모든 기부 자료에 10년을 적용하지 않는다.

**구현:**

- 해피나눔에서 필요한 원본을 적법하게 유지하는 것이 확인된 거래는 기존 `external_original` 분류를 활용해 앱 사본을 삭제한다.
- 앱에도 별도 보존 의무가 있는 거래만 기존 암호화 보관소에 최소 항목과 근거·기산일·종료일을 보관한다. 확인된 조직 규칙으로 자동 분류하고 예외만 기존 검토 절차에 남긴다.
- **운영자 결정으로 범위 변경:** 해피나눔·계좌이체 엑셀의 중복·신규 거래·탈퇴자 재반영 여부는 황제철 담당자가 업로드 전에 판단한다. 추가 자동 중복 판별, 거래 지문 보관, 실제 입금일 입력 강제는 이번 구현에서 제외한다.
- 파일 항목은 이름·기수·과·연락처·금액이며 고유 거래번호가 없다. 일괄 반영일자는 등록일이다. 등록일을 실제 기부일이나 법정 보존 기산일로 자동 간주하지 않는다.
- 담당자는 탈퇴자의 과거 개인정보 재반영과 모금 합계 이중 증가를 막도록 원본과 기존 반영 내역을 확인한다. 필요한 회계 원본을 앱에 재등록하는 대신 목적에 맞는 별도 보관소에서 관리한다.

**완료 기준:** 자동 재수입 방지를 구현했다고 주장하지 않고 위 운영 절차를 명시한다. 법정 보존 분류는 실제 원본과 검토된 기산일을 따른다.

## 4. Sentry의 실제 개인정보 경계 검증

프로젝트 교체는 완료됐으므로 다시 만들지 않는다. 신규 프로젝트 삭제를 매 회원 탈퇴마다 수행하는 구조도 만들지 않는다.

- 최종 iOS Release에서 로그인·쪽지·프로필·탈퇴 과정의 전송 내용을 격리된 검증 환경에서 확인한다. 테스트 데이터로 오류 원문, 사용자 ID, 요청 정보, 설치 식별자, 지역, 첨부파일, 캐시 재전송 누출을 검사한다.
- 회원과 연결되는 정보가 없는 것이 검증된 경로만 삭제 대상 없음으로 처리한다. 코드에 `setUser`가 없다는 사실이나 검색 결과 0건만으로 판단하지 않는다.
- 식별 가능한 정보가 발견되면 우선 수집 경로를 제거한다. 기존 저장 자료가 있으면 Sentry가 지원하는 실제 삭제 범위에 맞춰 별도 처리하고 증거를 남긴다. 존재하지 않는 사용자 DELETE API를 구현하지 않는다.
- Android는 연결 주소만 교체했고 iOS의 수집 제한과 동등하지 않다. Android를 같은 회원 서비스에서 운영할 경우 SDK 최소화와 실제 전송 검증을 공통 탈퇴 범위에 포함한다. iOS 심사 자체가 Android 기능 개발을 요구한다는 의미는 아니다.
- Sentry 공급자 백업의 만료와 장학회 서버 백업을 구분한다. 기존 테스트 프로젝트 삭제 결과를 모든 미래 회원의 외부 삭제 증거로 재사용하지 않는다.

**완료 기준:** 출시 후보의 실제 전송과 해당 없음/삭제 판정이 일치한다. 필요한 진단 기능과 심볼 해석도 확인한다.

## 5. 기존 관리자 화면·사용자 안내 보완

- 기존 관리자 삭제 목록에 지연된 저장소, 이유, 마지막 시도, 다음 작업을 표시한다. 불필요한 개인정보 원문은 표시하지 않는다.
- 기존 수동 전환·자동 재개 기능과 권한 검사를 유지한다. 이미 완료된 자동 작업을 수동 전환 후 반복하지 않는다.
- 처리 기한 초과 요청은 기존 관리자 목록에서 식별할 수 있게 한다. 새로운 외부 메일 발송 시스템은 이번 범위에 추가하지 않는다.
- 앱/웹 접수증에서 운영 데이터 삭제, 남은 처리, 보존 예외, 최종 완료를 일관되게 안내한다.
- 실제 적용 가능한 기간에 맞춰 개인정보처리방침의 3일 목표·10일 안내와 백업 설명을 최종 정리한다. 이는 장학회 운영 목표이며 Apple이 정한 일수는 아니다.

**완료 기준:** 관리자는 현재 막힌 작업을 알 수 있고, 사용자는 부분 진행을 최종 완료로 오해하지 않는다.

## 실행 순서와 출시 판정

1. 저장소 실사·기부 원본 기준 확인(0).
2. 작업 상태와 삭제 순서 보완(1).
3. 백업·파일 작업(2), 기부 재유입 방지(3), 실제 Sentry 경계 확인(4).
4. 기존 화면·개인정보처리방침 정합성 보완(5).
5. 격리 환경에서 DB·파일·기부·백업 복원·실패 재개 통합 검증.
6. 운영 마이그레이션 사전 점검, 비밀키·권한·작업 주기 설정, 배포.
7. 폐기 가능한 계정으로 실제 Apple/Kakao 철회와 삭제 완료 확인. 최종 iOS 아카이브, 로그인 3종·푸시·신고·외부 기부 이동, App Store 개인정보 답변을 확인한 뒤 제출.

이번 계획 작성은 운영 배포 승인이 아니다. 각 저장소에 맞는 실제 연동이 확인되기 전까지 자동 탈퇴가 운영에서 완성됐다고 판단하지 않는다.

## 근거와 적용 범위

[Apple 계정 삭제 안내](https://developer.apple.com/support/offering-account-deletion-in-your-app/)는 계정·연결 개인정보·사용자 콘텐츠 삭제와 법정 보존 예외, 처리 소요 시간 안내 및 완료 확인을 요구한다. 자동 처리 자체나 특정 백업 구현·특정 일수를 일률적으로 요구하는 것은 아니다. 이 계획의 작업 구조와 복원 검증은 해당 요구를 실제 서비스에서 이행하기 위한 구현 선택이다.

[Sentry 사용자 데이터 삭제 안내](https://www.sentry.help/en/articles/16187006-how-do-i-complete-a-gdpr-erasure-request-for-a-user-in-sentry)는 사용자 삭제 API의 부재와 자료 종류별 삭제 한계를 명시한다. 기부 관련 법적 근거와 기존 구현은 [자동 삭제 운영 문서](AUTOMATIC_ACCOUNT_ERASURE.md)를 기준으로 별도 검토한다.

## 구현 진행 — 2026-09-07

`feature/complete-account-erasure`에서 단계 분리와 암호화 작업 정보, 기존 요청 재개, 부분 진행 안내를 구현했다. 로컬 전체 Go 테스트·vet, MariaDB 10.1 자동/수동 삭제 테스트 및 두 SPA 빌드를 통과했다. 이 기록은 아래 나머지 항목의 완료를 의미하지 않는다.

남은 코드: 저장소별 작업 상태·처리기, 복원 방지 대장·재적용,  실제 Release 전송 검증 및 필요한 Android 수집 제한. 외부 기준: 가비아 백업·스냅샷과 해피나눔 원본 보존 설정 확인. 운영 배포·마이그레이션·실제 회원 삭제는 수행하지 않았다.

읽기 전용 서버 실사: `/var/www/legacy/files`는 `/var/www/html/upload`를 가리키는 심볼릭 링크다. `/var/www/uploads`, `/var/logs/pg`, `/var/backups/alumni-maintenance`가 존재한다. 확인한 systemd timer 및 `/etc/cron.d`, daily/weekly 목록만으로 호스팅 백업 유무·기간을 판정하지 않는다. 이 경로의 사용자 파일이나 백업 내용은 복사·삭제하지 않았다.

## 저장소별 진행 구현 — 2026-09-07

migration 060에서 백업, 과거 파일, 외부 서비스, 간접 참조를 각각 추적한다. 작업 상태는 대기·처리 중·완료·해당 없음·수동 확인·실패이며, 완료와 해당 없음에는 근거가 필요하다. 관리자 목록에서 항목별 상태·시도 횟수·최근 시도·확인 근거·후속 조치를 확인한다. 기존 수동 전환을 유지하고 검증된 항목은 재시도하지 않는다.

이 변경은 실제 가비아 백업 삭제 처리기나 독립적인 복원 방지 대장 구현을 완료한 것이 아니다. 설정을 확인한 뒤 저장소별 삭제 수단과 복원 통제를 연결해야 한다.

## 백업 범위 정정 — 2026-09-07

운영자는 가비아 자동 백업·스냅샷을 사용하지 않으며 예정된 서버 이미지 백업도 실행하지 않았다고 확인했다. 서버 유지보수 디렉터리 실사 결과와 한계는 [별도 기록](ACCOUNT_ERASURE_STORAGE_AUDIT.md)을 참조한다. 현재 회원 백업이 없는 것으로 확인되는 범위에서는 백업 삭제·복원 시스템의 신규 구축을 출시 전 일률적인 필수 작업으로 요구하지 않는다. 실제 백업 도입 시 보존·만료·복원 후 삭제 재적용을 연결한다. 외부 공급자 백업·현재 파일·기타 개인정보 삭제 확인은 별도다.
