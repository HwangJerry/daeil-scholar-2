# 독립 재검토에서 발견된 경계 조건

2026-09-07. 서버 후보 `29fd540`과 iOS `dee271678` 재검토에서 발견했다.
수정 전 서버 후보는 HOLD를 유지한다. 운영 배포나 실제 데이터 삭제는 승인 범위가 아니다.

## 왜 이전 테스트를 통과했는가

파일 참조 검사는 Go URL 파서가 절대 주소로 분류한 값을 외부 주소로 취급했다.
하지만 브라우저는 `https:/files/shared.jpg`를 현재 사이트 주소로 해석할 수 있다.
단일 파서 안에서 일관된 결과가 나오는지 확인하는 테스트만으로는 이 차이가 드러나지 않았다.

iOS 테스트 저장소의 `load()`는 접수된 확인번호만 반환했고, 실제 Keychain 저장소는
접수 여부가 불명확한 pending 확인번호를 먼저 반환했다. 따라서 같은 기기에서
A 탈퇴 접수 후 B 탈퇴 통신 실패가 발생하면 A를 조회할 수 없는 상황을 놓쳤다.

이전 검토는 정상 처리와 당시 알려진 실패 사례에 집중했다. 테스트 통과를 검증하지 않은
경계 조건까지 안전하다는 의미로 해석하면 안 된다. 독립 검토는 도움이 되었지만,
처음부터 실제 구성요소 간 동작 차이와 다중 계정 상태 전환을 포함했어야 했다.

## 이번 검증 기준

- 파일 주소: hostless HTTP(S), opaque 주소, 대소문자, 슬래시 변형을 포함한다.
  불확실한 참조는 외부 파일로 단정하지 않고 검토를 요구한다.
- 저장된 참조: 실제 MariaDB에서 프로필·게시물 HTML·썸네일·배너를 각각 검증한다.
  초기 큐와 마지막 삭제 검사 모두 구체적인 차단 사유를 확인하며, 삭제 콜백이 실행되지
  않고 작업이 보존되는지 확인한다. 단순 SQL 오류를 성공으로 계산하지 않는다.
- iOS: Keychain 입출력만 테스트 대역으로 바꾸고 실제 저장·선택 로직을 실행한다.
  기존 접수 확인번호와 접수 불명확 요청 모두 접근 가능해야 한다. 재시도, 계정 구분,
  기존 저장 형식, 저장 실패 복구도 유지해야 한다.

검증 결과는 해당 수정 커밋과 배포 후보에 연결한다. 로컬 테스트는 운영 파일 권한,
외부 제공자 철회, App Store 배포용 빌드와 실기기 검증을 대신하지 않는다.

## 수정 및 검증 결과

- HTTP(S) hostless/opaque 및 authority 복구가 필요한 주소는
  `FILE_PATH_REVIEW_REQUIRED`로 차단한다. 콘텐츠 추출도 HTTP(S) 토큰을 보존한다.
  불확실한 주소가 남아 있으면 자동 삭제가 검토 대기할 수 있는 의도적인 제한이다.
- 실제 MariaDB 신규 24조건과 기존 배너·엔티티·파일 안전성 회귀가 통과했다.
  전체 `go test ./...`, `go vet ./...`, 배포 Python 테스트 15개도 통과했다.
- iOS는 접수 내역을 목록으로 보존하고 기존 단일 확인번호를 유지한다. 로그인 화면에서
  접수 확인 완료/필요와 순번으로 요청을 선택한다. 저장 중간 실패에도 재시도할 수 있다.
  iOS 커밋 `16f2249`, 브랜치 `fix/account-deletion-receipt-retry`에서 전체 XCTest
  138개(신규 5개)가 통과했다. 화면 스크린샷/실기기 검증은 수행하지 않았다.
- 기존 iOS 사용자 작업트리의 디자인 변경에 통합하지 않았다. 서버 배포 묶음은 iOS
  바이너리를 포함하지 않으므로 해당 브랜치 통합과 제출용 빌드는 별도 단계다.
