# 회원 탈퇴 출시 준비 — 2026-09-07

운영 앱·DB 마이그레이션을 배포하거나 실제 회원을 삭제하지 않았다. 서버에는 기존 PG 로그의 접근 제한 검토본만 만들었다. Sentry 출시 프로젝트에는 격리된 시뮬레이터에서 발생시킨 합성 오류 2건을 전송해 검증했다.

## 이번에 구현·검증한 항목

- migration 062: 현재 프로필 사진·명함·썸네일의 관리 파일 경로를 별도로 기록한다. 이후 사진/명함을 교체할 때 이전 경로를 같은 트랜잭션에서 보존하고, 탈퇴 시 현재·이전 파일을 삭제 큐에 넣은 후 경로 이력을 지운다. 기존 파일 등록부에 행이 없어도 현재 연결을 잃지 않는다. 이미 연결이 사라진 더 오래된 파일의 소유권을 복원하는 기능은 아니다.
- 레거시 `/upload/`, `/old/upload/` URL을 확인된 실제 루트로 연결했다. BASE64 게시글의 레거시 이미지도 찾고, 과거 파일 등록 도구에서는 다른 회원/게시글/이력이 같은 파일의 별칭을 참조하는지 확인한다.
- 새 PG 감사 로그는 거래 대사에 필요한 승인 결과·거래 식별자·금액 등을 유지하고 카드 번호·자유 형식 응답/오류는 제외한다. 새 파일 권한은 `0600`이다. 보존 기간이나 거래 증빙의 익명성을 새로 주장하지 않는다.
- Debug Agent로 보내는 자유 형식 로그 메시지·브라우저 오류/URL/컴포넌트/스택을 제거했다. 서버 panic은 코드에서 생성한 Go 스택과 고정 문구만 전달한다. 과거 수신 데이터가 삭제된 것은 아니다.
- `cmd/pg-audit-sanitize`는 기존 로그를 덮어쓰지 않고 별도 검토본을 만든다. 모르는 필드/형식, 읽는 동안 바뀐 원본, 기존 출력 파일은 거부한다. 중간 실패 시 부분 결과를 게시하지 않는다.

Go 전체 테스트·vet, MariaDB 10.1.38 자동/수동 탈퇴 테스트, 파일 교체 이력·레거시 URL·탈퇴 후 변경 차단·로그 최소화 테스트를 통과했다. 프런트엔드 코드는 이번 단계에서 변경하지 않았다.

## 운영 실사 결과와 한계

- 회원 프로필 사진이 있는 계정은 3개다. 사진·명함·썸네일의 관리 경로는 레거시 별칭까지 합해 8개이며, 모두 실제 파일이 있다. 이 중 파일 등록부와 연결되지 않는 경로는 5개다. 새 migration이 현재 참조를 확보한다.
- 파일 등록부 188건 중 145건이 `/upload/`, 43건이 `/uploads/` 계열이다. 실제 파일 465개 중 정규화한 등록부 URL과 정확히 일치한 것은 43개였다. 나머지 422개를 삭제 대상이나 소유자 불명 개인정보로 단정하지 않는다. 본문 참조·변환 파일·공개 자산 등 추가 조사가 필요하다.
- PG 로그는 1개, 9행, 2,002바이트다. 카드 번호가 든 행 3개, 원문 오류가 든 행 5개를 확인했다. 값 원문은 출력하지 않았다.
- `/etc/logrotate.conf` 및 `/etc/logrotate.d/*`에서 앱/PG 로그 경로를 직접 지정한 설정은 찾지 못했다. 다른 glob·타이머·별도 작업까지 없다고 판정한 것은 아니며, 실제 회전 적용 확인은 남아 있다.
- Debug Agent는 운영 프로세스에서 활성화되어 있으나, 로컬 및 운영 호스트에서 API 문서를 조회하지 못했다. 요청한 서버 관리 접속 방법/소스/API 정보가 필요하다. 기존 HTTPS 삭제 처리기 계약에 실제 어댑터가 연결된 것으로 표시하지 않는다.

2. migration 040–062, 총 23개 후보 파일의 manifest SHA-256:
   `3d771b1a76cced492f019ef200262bc5acd5e678b21e24c5f24d4dc4afc88bcc`.
   소스·회귀 테스트·환경 예시를 맞췄으며 운영 승인 값은 바꾸지 않았다. 058의 엔진 변환은 잠금·디스크 여유·실행 시간을 검토해야 한다.
3. 운영 서버의 `/var/tmp/dflh-pg-review.6jlOcX/pg-audit.minimized.log`: `0600`, 1,408바이트, 9건의 검토본. 원본의 시각·주문 번호·이벤트 및 기존 대사 필드가 유지되고 카드 번호 필드·원문 오류가 없는 것을 확인했다. 검토용 실행 파일은 삭제했다.
4. 원본 PG 로그의 준비 전후 SHA-256은 모두
   `f53b1fb783e3600db2c8259d8033118c95bab6b3c9d5da6c29428fbe02a8184e`.
   실제 교체 시에는 기록 중인 프로세스를 통제하고 **다시 최신 원본으로 생성**해야 한다. 오래 열린 파일 핸들이나 이후 추가된 결제 기록을 잃지 않도록 원본을 단순 덮어쓰지 않는다. 적용 후 검토용 사본도 정리한다.

정리본은 거래 식별자가 남는 제한된 회계 자료이며 익명 자료가 아니다. 원본/정리본의 보존 근거·기산일은 기존 거래별 결정과 맞춰야 한다. 해피나눔·별도 엑셀의 진행 중 영수증 업무 및 연락처 정리 확인은 기존 담당자 업무를 유지한다.

## iOS 검증

수정한 Swift 앱으로 App Store 형식의 IPA 내보내기, 실제 서명 검사, 앱/SDK 개인정보 매니페스트 5개와 운영 API 설정 검사를 완료했다. 최종 IPA의 APNs는 `production`, `get-task-allow`는 `false`, Apple 로그인 권한은 포함되어 있다.

Sentry의 실제 최종 HTTP 전송 경로를 Release 설정에서 검사하는 테스트를 추가했다. 실제 합성 crash 수신에서는 기존 필터가 필수 `debug_meta.images[].code_file`을 제거하는 오류를 발견했고, 개인정보가 없는 시스템 경로/알려진 앱 모듈 이름만 보존하는 `crash-only-v2`로 수정했다. 수정 후 이벤트는 사용자 식별정보가 없고 처리 오류도 없었다. 15개 스택 프레임 중 13개 함수가 해석되었다. 모든 앱 프레임의 dSYM 해석까지 완료했다고 주장하지 않는다.

Swift 저장소의 `docs/operations/RELEASE_ERASURE_VERIFICATION.md`에 최종 IPA와 재현 절차를 기록한다. TestFlight 업로드나 App Store 제출은 하지 않았다. 운영 로그인 3종·Apple 토큰 철회·APNs 수신·실제 탈퇴는 최신 백엔드 배포 후 폐기 가능한 계정으로 검증해야 한다.

## 실제로 남은 일

- Debug Agent 저장 데이터의 조회/삭제 API를 확인하여 실제 외부 처리기를 연결하거나, 기존 수동 절차로 실삭제 근거를 확보한다. 연결되지 않은 항목을 자동 완료시키지 않는다.
- 연결이 끊긴 과거 파일은 근거를 확인한 목록만 기존 삭제 큐로 보낸다. 이름·파일명만으로 소유자를 추측하지 않는다.
- 운영 변경 적용: 키 주입, 마이그레이션, 백엔드/웹/관리자 배포, PG 검토본의 최신화 및 통제된 교체, 실제 로그 회전 설정 검증. 현재 진행한 검증은 운영 반영을 대신하지 않는다.
- 실제 설치 후보에서 로그인·탈퇴·신고/차단·외부 기부·푸시·정책 링크와 reviewer 계정을 검증한다.
