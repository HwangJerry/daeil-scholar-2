# Apple 심사 기준 계정 삭제 범위 검토

2026-09-06. 현재 저장소의 Go 코드·SQL 마이그레이션과 Apple 공식 안내를 대조한 구현 제안이다. 운영 DB의 전체 스키마·데이터·파일을 실사하거나 실제 삭제한 결과는 아니다. 추가 한국 법률·세무 조사는 이번 범위에 포함하지 않는다.

## Apple 기준과 구현 원칙

Apple은 계정 전체와 연결된 개인정보를 삭제하도록 요구한다. 계정 비활성화만으로는 부족하다. 다른 이용자에게 공유한 사진·글 등 사용자 생성 콘텐츠도 포함한다. 법적으로 보관해야 하는 자료는 예외지만, 모든 기부 내역이나 신고 기록에 예외가 자동 적용되지는 않는다.

앱에서 요청을 받고 운영자가 실제 삭제하는 방식은 허용된다. 소요 기간과 완료 결과를 알려야 하며, 일반 앱에서 접수를 위해 별도 이메일·전화 연락을 강요하면 안 된다. Apple 로그인 토큰은 REST API로 철회한다. 근거: [Apple 계정 삭제 안내](https://developer.apple.com/support/offering-account-deletion-in-your-app/).

아래 테이블별 방법, 양방향 쪽지 삭제, 익명 집계 유지 등은 이 앱에 대한 구현 제안이다. Apple이 특정 SQL이나 동일한 저장 기간을 지정한 것은 아니다.

개인을 다시 연결할 수 없는 전체 모금액·방문자 수 같은 집계는 유지하는 설계를 권장한다. 예를 들어 `DONATION_SNAPSHOT`, `WEO_VISIT_SUMMARY`는 개인별 원본과 구분한다. 다만 거래별 금액·시각·거래번호를 남긴 행이나 회원 ID를 해시한 행을 곧바로 익명 집계로 취급하지 않는다. 모금 총액이 탈퇴 때문에 줄거나 다음 집계에서 삭제 전 수치로 잘못 복원되지 않도록 집계 로직도 함께 검증한다.

## 현재 구현에서 발견한 누락

1. 새 삭제 API와 관리자 화면은 접수·철회 요청·검증·완료 관리 기능이다. 실제 DB·파일 전체 삭제 실행기는 없다. 레거시 `AnonymizeAccountForDeletion`도 이름과 달리 `USR_STATUS='AAA'` 처리다.
2. `account_deletion_verification.go`는 특정 컬럼 이름만 검색한다. `WEO_VISIT_DAILY.VD_USR_SEQ`, `WEO_ORDER.O_ACCOUNT_USR_SEQ`가 목록에 없다. 따라서 현재 화면의 잔여 건수 0은 전체 삭제 증명이 아니다.
3. 이메일 기반 인증 자료, `IDENTITY_ID`·주문 번호·게시글 번호를 통한 간접 참조, 신고 본문 사본과 파일은 별도 검증이 필요하다. 번호가 우연히 같은 다른 종류의 ID를 회원 번호로 간주해서 삭제하면 안 된다.
4. 프로필/명함 업로드는 무작위 파일명으로 저장하고 `WEO_FILES.F_JOIN_SEQ=0`으로 기록한다. 프로필 경로를 교체할 때 이전 파일의 회원 소유 이력을 기록하지 않는다. 현재 URL만 지우면 과거 업로드가 남을 수 있다. 앞으로 업로드 소유 정보를 남기고 기존 파일은 확인 가능한 연결을 조사해야 한다. 같은 디렉터리의 모든 파일을 삭제하는 방식으로 해결하지 않는다.
5. 기부 자료의 별도 개인정보, 스토리지·Sentry·백업은 현 관리자 체크박스만으로 자동 삭제되지 않는다. 외부 작업 실패나 미확인 자료가 있으면 완료로 표시하지 않아야 한다.

## 구현 순서와 검증 기준

1. 회원의 직접·간접 ID, 소유 파일, 법정 보존 분류를 파악하는 읽기 전용 계획을 생성한다. 실제 배포 스키마·FK·트리거·스토리지 엔진을 대조한다. 개인정보 원문을 일반 로그에 출력하지 않는다.
2. 기존 요청 접수 즉시 접근 차단을 유지하고, 모든 기기의 세션과 발송 대기를 정리한다. Apple/Kakao 철회는 재시도 가능한 작업으로 실행한다.
3. 검토된 테이블별 삭제기를 구현한다. 임의의 컬럼명 검색 결과를 그대로 DELETE로 바꾸지 않는다. 운영자가 실행하는 방식이어도 좋으며, 여러 번 실행해도 다른 이용자 자료가 손상되지 않아야 한다.
4. 파일 삭제는 재시도 작업으로 추적한다. DB와 파일·외부 서비스 작업을 단일 SQL 트랜잭션처럼 취급하지 않는다. 일부 실패 후에도 상태와 삭제 대상을 잃지 않게 한다.
5. 회원 행은 필요한 식별자·파일 작업을 안전하게 확보한 후 제거한다. 소셜 철회 성공 증거는 기존 완료 검증에 필요한 동안만 유지한다. 백업 복원 대응에 필요한 제한된 매핑도 필요 기간 후 제거한다.
6. 독립적인 잔여 검사와 외부 작업 확인 후 완료 처리·통지한다. 접수증에는 불필요한 개인정보를 넣지 않는다.

가상 계정 두 개로 다음을 검증한다: 탈퇴자 프로필·작성 콘텐츠·신고 사본·기부 개인정보·직간접 인증 데이터·파일 삭제, 다른 회원의 독립 자료 보존, 쪽지 양쪽 화면 반영, 재로그인·기존 세션·push 차단, 소셜 철회 실패/재시도, 중간 파일 삭제 실패 후 재개, 모금 집계 보존, 완료 결과 조회. 실제 공급자 철회와 외부 저장소 처리까지 검증하기 전에는 릴리스 후보의 삭제가 검증됐다고 표시하지 않는다.
