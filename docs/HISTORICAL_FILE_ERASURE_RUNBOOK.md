# 과거 업로드 파일 삭제 연결

2026-09-07. 운영 배포·운영 데이터 삭제는 하지 않았다.

## 구현된 범위

`backend/cmd/erasure-files`는 개발자/서버 운영자가 소유 관계를 검토한 과거 파일을 기존 자동 삭제 큐에 등록하는 도구다. 소유자를 파일명·회원 이름으로 추정하지 않는다. 기존 관리자 수동 처리 기능은 유지한다.

- 앱 DB 삭제가 끝난 자동 처리 요청에만 등록한다. 요청 번호와 탈퇴 회원 번호를 대조한다.
- `ownershipVerified`, `retentionRespected`와 개인정보가 없는 검토 증빙 번호가 필요하다. 확인 표시는 실제 소유권·보존 검토를 대체하지 않는다.
- 현재 회원 사진·명함, 업로드 소유권, 연결된 첨부파일, 일반/BASE64 게시글 본문에서 참조되는 파일은 차단한다. 이 검사는 모든 레거시 표현이나 외부 참조의 전수 증명이 아니다. URL 별칭·HTML 엔티티 등도 원본 조사에서 대조한다.
- `/uploads/`, `/files/` 아래의 정규 상대 URL만 받는다. 외부 URL, 경로 이동, 인코딩 우회, 중복 입력은 거부한다.
- 실제 루트가 없거나 심볼릭 링크인 경로는 거부한다. 파일만 이미 없어졌다면 재시도를 허용한다.
- 등록은 트랜잭션이고 동일 경로의 재등록은 중복 큐를 만들지 않는다. 실행 중에는 자동 작업과 같은 DB 잠금을 사용한다.
- 실제 삭제는 다음 자동 작업이 수행한다. Linux/macOS에서는 디렉터리 핸들을 따라 `O_NOFOLLOW`로 열고 `unlinkat`으로 삭제하여 검사 직후 디렉터리가 링크로 바뀌어도 외부 경로를 따라가지 않는다.
- 파일을 등록하거나 큐를 비웠다는 이유로 `historical_files` 전체를 완료 처리하지 않는다. 미확인 과거 파일과 외부 저장소는 기존 확인 절차에 남는다.

## 사용 방법

배포 후보 backend와 같은 DB 환경 변수를 사용한다. 앱 DB 삭제 이후에도 기존 비공개 관리자 요청에서 대상 요청/회원 번호를 확인할 수 있다. 입력 파일은 서버의 공개 업로드 폴더가 아닌 접근 제한 작업 폴더에 두고 권한은 `0600`으로 설정한다. 작업 완료 후 식별번호·경로가 담긴 입력 파일은 정리하고 개인정보 없는 증빙 번호만 유지한다.

아래는 가상 예시이며 실제 운영 대상이 아니다.

```json
{
  "requestId": 1,
  "userSeq": 42,
  "evidenceReference": "inventory-review-42",
  "ownershipVerified": true,
  "retentionRespected": true,
  "files": ["/files/profile/old42.jpg"]
}
```

backend 디렉터리에서:

```sh
go run ./cmd/erasure-files -file /private/operations/reviewed-files.json
go run ./cmd/erasure-files -file /private/operations/reviewed-files.json -apply
```

첫 명령은 파일·요청 상태·참조 관계를 확인하며 DB/파일을 바꾸지 않는다. `-apply`는 큐를 등록하고 다음 자동 작업을 예약한다. 개인정보가 출력되지 않도록 오류에는 SQL·파일 경로·접속 정보를 포함하지 않는다. 재등록 후에는 관리자 화면의 항목별 상태를 확인한다. 마지막 계획의 검토 증빙 번호가 `reviewed-file-plan:` 접두사로 표시되며, 전체 조사 증빙은 별도 운영 기록에서 관리한다.

## 운영 경로 확인

읽기 전용 실사에서 `/var/www/legacy/files`의 실제 경로는 `/var/www/html/upload`다. 기존 파일 제공 설정을 바꾸지 않고 삭제 작업만 다음 환경 변수로 실제 경로를 지정할 수 있다.

```text
ACCOUNT_ERASURE_LEGACY_ROOT=/var/www/html/upload
```

미설정 시 `UPLOAD_LEGACY_PATH`를 사용한다. 심볼릭 링크 경로를 유지한 채 검사를 생략하지 않는다. 백엔드 서비스 계정 `alumni-backend`으로 두 루트의 쓰기 가능 여부를 확인했으나, 모든 하위 디렉터리·서비스 격리 설정에서 실제 삭제한 결과는 아니다. 운영 테스트 계정의 파일로 최종 검증한다.

## 아직 연결되지 않은 부분

이 도구는 Sentry·Debug Agent·Apache/journal·결제 로그를 지우는 외부 처리기가 아니다. 기존 HTTPS 외부 처리 계약에는 실제 저장소 어댑터가 여전히 필요하다. 저장소에 귀속 가능한 데이터가 없음을 확인한 경우에는 해당 범위의 근거를 사용한다. 비어 있는 외부 처리 URL을 성공으로 취급하지 않는다.

소스에서 확인한 `PGAuditLogger`는 거래 번호, 카드 번호 등을 포함할 수 있는 PG 응답, 오류 문자열을 기록한다. 회계 증빙 보존 범위와 함께 검토하며 일반 오류 로그처럼 일괄 삭제하지 않는다. Debug Agent 사용 여부와 실제 수신 데이터, Apache 과거 `combined` 로그도 별도 확인 대상이다.

## 검증

- Go 전체 테스트·vet 및 Linux amd64 도구 빌드.
- MariaDB 10.1.38 합성 계정: dry-run 무변경, 잘못된 회원 차단, 다른 회원 사진/BASE64 게시글 참조 차단, 수동 전환 존중, 중복 등록 방지, 파일 큐가 남으면 완료 차단.
- 실제 임시 파일: 잘못된 루트에서는 작업 유지, 경로 수정 후 삭제·다른 파일 보존, 외부 확인 누락 시 최종 완료 차단.
- 경로 검사 후 디렉터리를 심볼릭 링크로 교체해도 외부 파일을 삭제하지 않는 회귀 테스트.

운영 삭제, 외부 서비스 삭제 및 실제 iOS Release 종단 검증 결과를 의미하지 않는다.

추가 운영 관측: Debug Agent는 실행 중인 백엔드에서 활성화되어 있다. 자동 삭제용 키·외부 처리 URL/토큰·실제 레거시 루트 설정은 아직 없다. Sentry 출시용 두 프로젝트의 최근 14일 오류 이벤트 조회는 모두 0건이었으므로, 실제 Release 오류 전송을 별도로 검증해야 한다. 설정 여부와 조회 범위는 [실사 기록](ACCOUNT_ERASURE_STORAGE_AUDIT.md)을 참조한다.
