## 1. P1 — 다른 회원 소유 파일이 자동 삭제 큐에 들어간다 (재현됨)

위치: `backend/internal/repository/account_erasure_database.go:85`, 특히 120–128행.
`postErasureURLs`는 탈퇴자 게시글에 포함된 관리 경로를 수집한다.
자동 큐 생성에는 다른 회원의 소유권·참조 검사가 없고, 같은 URL의 `WEO_FILES`도 소유자 제한 없이 삭제한다.
역사 파일 수동 등록 경로에는 참조 검사가 있지만 이 자동 경로에는 호출되지 않는다.

로컬 MariaDB 10.1.38에 합성 회원 A/B를 만들고 A의 게시글에서 B 소유 이미지를 참조했다.
`queueErasureFiles` 실행 결과 B 파일이 큐에 1개 등록됐고 B의 파일 메타데이터가 0개로 줄었으며 B 소유권 행은 1개 남았다.
이 테스트는 트랜잭션 안에서 결과를 확인하고 롤백했다. 실제 운영 파일 삭제나 운영 영향 건수 조사는 하지 않았다.
큐를 처리하는 서비스는 관리 경로·심볼릭 링크를 검사하지만 소유권은 다시 확인하지 않아 실제 파일 삭제로 이어질 수 있다.

필요 조치: URL 참조와 소유권을 구분하고, 타인 소유·공유 파일은 삭제를 차단하여 검토 대상으로 남긴다.
파일 등록 정보 삭제에도 소유자/게시글 범위를 적용한다. 경로 별칭과 실제 파일 삭제 시점의 참조 재검증을 포함한다.

## 2. P1 — 외부 프로필 이미지 때문에 DB 삭제 후 처리가 멈춘다 (재현됨)

위치: `backend/internal/repository/account_erasure_database.go:90`,
`backend/internal/service/account_erasure_files.go:27`, `backend/internal/service/account_erasure.go:130`.

프로필 URL은 외부 주소도 로컬 파일 큐에 들어간다. 카카오 프로필 URL을 저장하는 기존 가입 경로가 있다.
로컬 삭제기는 외부 호스트를 `FILE_PATH_REVIEW_REQUIRED`로 거절한다.
서비스는 이 오류를 만나면 외부 처리 단계까지 도달하지 못하고 동일 큐를 재시도한다.

서비스 합성 저장소와 실제 경로 검증기를 조합해 외부 아바타 URL을 입력했다.
결과: DB 삭제 호출 1회, 파일 큐 1개 잔류, 외부 처리 호출 0회, `FILE_PATH_REVIEW_REQUIRED`.
이 검사는 실제 카카오 접속이나 실계정 DB 삭제를 하지 않았다.

필요 조치: 앱이 소유한 로컬 파일, 공급자 소유 아바타, 앱 소유 외부 파일을 구분한다.
외부 URL을 무조건 로컬 파일 삭제 큐에 넣지 않고, 외부 처리가 필요한 항목은 검증 가능한 별도 경로로 전달한다.

## 3. P1 — 설정 미완료를 배포 성공으로 오인할 수 있다 (코드·앞선 운영 관측)

위치: `backend/cmd/server/wire.go:242`, `backend/internal/repository/account_deletion_request_repo.go:60`, `deploy.sh:180`.
암호화 객체 생성 오류는 서버 조립 시 무시된다. 서버는 시작하며 탈퇴 요청을 접수하고 계정 접근도 차단한다.
필수 키가 없으면 워커가 실제 삭제 단계에서 보류된다. 전체 사이트 기동 실패나 nil 패닉으로 확인된 것은 아니다.
앞선 운영 관측에서 탈퇴 context/archive 키와 외부 처리 URL/token은 미설정이었다.
배포 스크립트는 새 설정을 검사하거나 주입하지 않는다.

키를 넣어 DB/파일 삭제가 가능해져도 외부 연결이나 관리자 저장소별 증빙 처리가 준비되지 않으면 최종 완료는 계속 보류될 수 있다.
Sentry 관리자 조회 설정도 아직 기존 프로젝트 이름이므로 출시 프로젝트의 오류를 제대로 조회하지 못할 수 있다.

필요 조치: 기능 활성화 전에 설정·파일 루트·외부 처리 또는 관리자 증빙 경로를 검사한다.
격리 환경에서 실제 설정과 동일한 조건의 탈퇴 완료를 확인하고, 불완전한 설정으로 접수만 활성화하지 않도록 한다.

## 4. P1 — 배포 실패 시 DB·웹·백엔드 버전이 섞일 수 있다 (기존 스크립트 위험)

위치: `deploy.sh:431`, `deploy.sh:461`, `deploy.sh:502`, `deploy.sh:529`, `deploy.sh:570`.

- 마이그레이션을 먼저 적용한 뒤 Go/npm 빌드를 한다. 빌드 실패 시 DB만 새 상태가 된다.
- 새 웹을 제공한 후 백엔드를 재시작한다. 그 사이 새 API 화면은 구버전 API에 접속한다.
- 사용자 웹 교체 후 관리자 전송이 실패하면 백엔드를 재시작하지 못하고 부분 배포 상태로 종료할 수 있다.
- `rsync --delete`로 이전 웹 자산을 제거하므로 이미 열린 페이지의 지연 로딩 파일 요청이 실패할 수 있다.
- 마지막 검사는 레거시 페이지의 상태 코드를 출력할 뿐 API 정상 응답을 강제하지 않는다. 자동 원복도 없다.

필요 조치: 검증한 산출물의 업로드를 먼저 끝내고 전환한다. 새 API 준비 확인 뒤 웹을 전환하고,
API 건강 상태 검사와 단계별 실패 복구를 추가한다. 일정 기간 이전 해시 웹 자산을 유지한다.

## 5. P1 — DB 변경·자동 삭제의 복구 수단이 현재 충분하지 않다 (운영 준비 위험)

위치: `backend/migrations/058_convert_erasure_tables_to_innodb.sql:24`, `backend/cmd/server/main.go:85`.
앞선 읽기 전용 관측 기준 058은 기존 MyISAM 테이블 8개를 InnoDB로 변환한다.
행 삭제 마이그레이션은 아니지만 테이블 재구축과 잠금이 발생할 수 있고 파일 전체가 원자적으로 롤백되지 않는다.
디스크 여유 확인만으로 해당 서버에서의 실행 시간·메모리 부담을 검증한 것은 아니다.

서버 시작 즉시 자동 탈퇴 및 보관 만료 작업이 실행되며 둘의 전역 비활성화 설정은 없다.
등록된 요청의 조건이 충족되면 실제 DB/파일 삭제가 진행될 수 있다. 과거 AAA 회원 일괄 삭제와는 별개다.
현재 확보한 것은 애플리케이션 파일 사본이다. 사용자가 확인한 운영 DB/파일 백업은 없으며 삭제 복구 테스트도 하지 않았다.

필요 조치: 058 실행 시간과 중간 실패 재개를 격리 환경에서 확인하고 운영 작업 시간을 확보한다.
필요 범위의 사전 복구 자료와 복원 절차를 준비한다. 서버 전체 이미지 백업 체계를 새로 구축해야 한다는 뜻은 아니다.
기능 전환과 작업 실행을 제어할 수단 및 테스트 계정으로 단계적으로 검증할 절차를 마련한다.

## 6. P2 — 외부 확인 지연 시 10일 후 자동 재개에 필요한 정보가 사라진다 (코드 확인)

위치: `backend/internal/repository/account_erasure_context.go:11`,
`backend/internal/repository/privacy_retention_repo.go:23`, `backend/internal/service/account_erasure_context.go:46`.
DB 삭제 전에 별도 암호화한 식별 정보는 생성 후 10일이면 만료되어 지워진다.
진행 중인 영수증 업무도 외부 처리 호출을 보류하므로 장기 업무에서는 만료가 먼저 올 수 있다.
이미 회원 행이 삭제됐으면 외부 미확인 항목의 자동 재개가 어려워져 수동 검토가 필요하다.
이는 거짓 완료로 처리되는 결함은 아니며, 저장소별 증빙을 실제로 확보하면 수동 확인을 거쳐 완료할 수 있다.

필요 조치: 만료 전 경고·담당자 확인, 지연 업무와 외부 식별자 처리의 순서, 만료 후 복구 절차를 검증한다.
단순히 기간을 무제한 연장하는 방식으로 해결하지 않는다.

## 7. P2 — 검토 묶음과 기존 배포 명령의 실행 범위가 다르다 (준비 자료 보완)

위치: `deploy.sh:463`, `deploy.sh:551`.
스크립트는 준비된 tar를 사용하지 않고 다시 빌드한다. 따라서 검증한 파일 해시와 실제 전송 파일의 동일성이 보장되지 않는다.
작업공간에서 재빌드하면 앞서 발견한 상위 Git 커밋 기록 문제도 다시 나타날 수 있다.
또한 구성요소 선택과 무관하게 레거시 PHP shim 3개를 업로드한다.
이 파일은 후보와 운영 백엔드 커밋 사이 소스 변경은 없지만, 운영 파일과의 개별 비교·복구 사본은 이번 준비에 포함되지 않았다.
기존 검토 묶음에는 이 3개 파일이 없으므로 스크립트의 모든 쓰기 대상을 포괄하는 완전한 복구 묶음은 아니다.

필요 조치: 배포 파일을 고정해서 사용하고 모든 쓰기 대상의 목록·비교·복구 범위를 일치시킨다.
