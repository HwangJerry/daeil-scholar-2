# 계정 삭제 수동 처리 운영 절차

2026-09-06 작성. 담당: **황제철 · ghkdwp018@naver.com**. 개인정보 보호 담당: 엄은숙.

이 문서는 새 릴리스의 운영 절차다. 운영 서버에 적용하거나 실제 회원 자료를 삭제한 기록이 아니다. 관리자 화면은 접수·검증·완료를 관리하며 **DB·파일 전체 삭제 버튼은 제공하지 않는다**. 실제 삭제는 서버 관리자와 담당자가 아래 절차로 수행해야 한다. 회원 상태를 `AAA`로 바꾸는 것만으로 완료하면 안 된다.

## 출시 전 준비

- migration 056과 백엔드, frontend, admin을 먼저 배포한다. iOS는 새 API가 동작한 뒤 배포한다. 기존 DELETE `/api/auth/account`도 새 접수 처리에 연결되지만, 접수증을 보관하는 새 iOS 버전을 출시 후보로 사용한다.
- `WEO_MEMBER`, 요청/권한 테이블 및 관련 트리거 대상의 InnoDB 여부와 배포 DB의 실제 컬럼·FK를 확인한다. 회원 테이블이 비트랜잭션이면 새 요청 API는 실패하도록 되어 있다. 스토리지 변환은 데이터 규모·락 영향을 별도로 검토한다.
- 황제철이 root 권한으로 `/admin/account-deletions`에 접근할 수 있어야 한다. 일반 관리자는 목록만 열람할 수 있고, root만 작업 시작·DB 조회·완료할 수 있다. 운영 권한 부여나 계정 생성은 이 작업에서 실행하지 않았다.
- 로그인/인증 대기 계정 모두 요청 가능하며 계정 이용 중지는 즉시 반영된다. 요청 접수와 관리자 권한 제거는 한 트랜잭션이다. 세션 정리 오류가 나도 접수 성공을 취소하지 않으며, 인증 미들웨어는 탈퇴 계정의 이용을 거부한다.
- Apple 키·토큰 암호화 키와 Kakao 설정, 소셜 철회 worker 동작을 실제 릴리스 환경에서 확인한다. 저장된 권한 철회 자격증명이 없는 기존 소셜 계정은 실제 공급자 철회 방법을 확보하기 전까지 완료할 수 없다.
- **백업 7일 순환**과 **Sentry 30일 이하**는 아직 운영 설정이 확인되지 않은 목표다. 적용 가능한 설정과 실제 선택 삭제 방법을 확인해야 한다. Sentry는 요금제·데이터 종류에 따라 30~90일 등 기간이 다르며 일괄 변경할 수 있다고 가정하지 않는다. 설정 변경 전 수집된 자료의 기간도 별도로 확인한다.
- 백업·Sentry·파일·간접 식별자까지 처리 가능한 서버 관리자와 실제 삭제 테스트를 완료해야 한다. 개인정보처리방침만 먼저 배포해 수동 삭제가 이미 운영되는 것으로 만들지 않는다.

## 매일 처리할 일

1. 접수/처리 중 목록을 매일 확인한다. 접수일+3일은 처리 목표, +10일은 처리 결과 안내 기한이다. 10일이 추가 보관 유예기간은 아니다. 부재 시 대리 처리자를 정한다.
2. 요청 번호로 작업대장을 만들고, 본인의 요청을 스스로 승인하지 않는다. 신원이 확인된 앱 요청에 다시 이메일을 보내야만 접수되는 절차를 요구하지 않는다.
3. 삭제 전에 결과 통지에 필요한 기존 연락 수단과 파일·외부 서비스 식별자를 접근 제한 작업 공간에서 확인한다. 비밀번호·토큰·PII 원문을 관리자 증빙 칸이나 일반 이슈에 붙이지 않는다. 통지에 필요한 임시 연락 자료도 발송 후 지체 없이 제거한다.
4. **작업 시작 · 소셜 권한 철회 요청**을 누른다. 이때 AP/KT의 `ACCOUNT_DELETE` outbox 작업을 만들고 worker가 실제 공급자 철회를 수행한다. 인증 토큰이나 소셜 연결 행을 먼저 지우지 않는다.
5. 아래 법정 보존 자료를 판별하고, 필요한 항목만 별도 접근 제한 보관소로 옮긴다. 확인되지 않은 의무를 이유로 전체 회원정보를 남기지 않는다. 복사본까지 보존대장에 위치와 만료일을 기록한다.
6. DB/파일/외부 자료를 실제 삭제한다. 아래 점검 범위에 따라 서버 관리자가 해당 배포 스키마를 검토해 삭제 쿼리를 작성한다. 먼저 SELECT로 대상과 건수를 확인하고 다른 회원 자료를 건드리지 않는지 확인한다. FK의 자식부터 처리한다. 공용 파일은 소유 관계를 확인한다. 법정 보존 자료를 분리한 후 운영 DB의 개인 연결을 제거한다.
7. **남은 데이터 조회**를 실행한다. 회원 번호 참조가 남으면 완료가 차단된다. 이 조회는 알려진 컬럼 이름을 기준으로 하므로 이메일·전화번호·소셜 ID·다른 ID를 통한 간접 참조와 파일 검토를 대신하지 않는다.
8. 백업의 선택 삭제/만료, 복원 시 삭제 재적용, 외부 처리자의 해당 자료 삭제까지 확인한다. 백업 교체를 기다리는 경우 통상 3일 목표를 넘길 수 있으므로 담당자가 일정을 관리한다. 기한 내 해결하지 못하면 즉시 사유와 조치 일정을 개별 안내한다. 미완료 상태를 완료로 바꾸지 않는다.
9. 모든 실제 삭제를 검증한 뒤 이용자에게 완료일, 삭제 범위, 남긴 법정 자료의 항목·근거·항목별 종료일, 거절 범위의 사유와 이의제기 방법을 **개별 통지**한다. 자동 이메일 발송 기능은 없다. 이메일을 쓸 경우 기존 확인된 주소로 담당자가 발송하고 증빙 번호를 남긴다. 연락 불가 사례의 적법한 통지 방법은 별도로 정한다.
10. 관리자 확인 항목과 작업/발송 증빙을 입력하고 완료한다. 법정 보존 자료가 없으면 정확히 `없음`, 있으면 항목별 근거·기간과 종료일을 적는다. 여러 항목의 상세 기간은 안내문/보존대장에 기록하고 날짜 필드에는 마지막 종료일을 넣는다. 완료 API는 DB 잔여 기록과 이번 요청의 AP/KT 철회 증빙을 다시 확인한다.
11. 완료 시 접수증의 회원 번호 연결과 공급자 철회 작업 기록을 제거한다. 사용자는 로그인 화면의 ‘계정 삭제 처리 현황’에서 결과를 조회할 수 있다. 서버는 확인번호 원문 대신 SHA-256만 저장하며, 조회 API는 POST·no-store·요청 제한을 적용한다. 결과는 완료 후 30일간 제공하고 이후 정리한다.

## 실제 삭제 점검 범위

- `WEO_MEMBER` 전체 회원 행: 인증/개인정보를 비워둔 회원 행도 자동 검증은 완료로 인정하지 않는다.
- `WEO_MEMBER_SOCIAL`, `ALUMNI_SOCIAL_CREDENTIAL`: 공급자 철회 성공 후 제거. `ALUMNI_SOCIAL_REVOCATION_OUTBOX`의 성공 증빙은 완료 API가 제거하므로 그 전에 삭제하지 않는다.
- 세션·refresh·비밀번호 재설정·인증번호·push token·알림 발송 대상·이벤트 분석 데이터. 전달 대기 중 push/email 큐와 캐시도 확인한다.
- 적용된 경우 `AUTH_ACCOUNT_STATE`, `AUTH_IDENTITY`, `AUTH_PASSWORD_CREDENTIAL`, `AUTH_PROVIDER_CREDENTIAL`, `AUTH_SESSION_FAMILY`, `AUTH_PHONE_CLAIM`, `AUTH_CONSENT`와 revoke outbox. 실제 FK와 이중 쓰기 트리거를 확인해 자식부터 삭제한다.
- `ALUMNI_MESSAGE` 송신/수신 행, 차단 관계, `ALUMNI_MESSAGE_REPORT` 신고자/대상자 증거, 알림, 게시글·댓글·첨부파일 등 사용자 생성 콘텐츠. 상대방에게 공유된 사본도 포함한다. 법정 증거만 별도 보관한다.
- `WEO_ORDER` 및 기부/회원 연결: 회계 담당자가 판별한 법정 보존 항목만 별도 보관하고 앱에 표시하는 연결과 불필요한 사본을 제거한다. 해피나눔 원본의 처리 책임·삭제 요청 전달 범위는 계약과 실제 제공 관계를 확인한다.
- 프로필 사진·업로드 원본·썸네일·내보내기 파일·CDN 캐시·관리자가 다운로드한 사본.
- 이메일/전화/이름/소셜 ID 등 직접 식별자, 다른 레코드를 통한 간접 연결. 관리자/승인자 ID 등도 점검하고 의무 보존 대상은 별도로 관리한다.
- Sentry의 이벤트·첨부·trace·replay·사용자 문맥과 관련 이메일. `sendDefaultPii=false`만으로 개인정보가 전혀 없다고 단정하지 않는다.
- DB snapshot, 파일 backup, 외부 보관본. 복원은 격리 환경에서 하고 삭제 요청을 재적용한 후 서비스에 연결한다. 삭제 대상 식별 매핑은 복원 대응에 필요한 기간만 접근 제한 보관하고 모든 해당 백업 만료 후 제거한다.

DB 조회는 회원 번호 관련 컬럼만 조회하는 **보수적인 진단 도구**다. 운영 DB의 모든 개인정보 위치를 자동 발견하거나, 법정 보존 예외를 자동 판단하거나, 운영 자료를 직접 삭제하는 기능은 아니다.

## 법정 보존대장 (별도 접근 제한 저장소)

| 항목 | 필수 기재 내용 |
| --- | --- |
| 작업 연결 | 요청 번호, 기록 분류, 보존 위치와 접근 담당자 |
| 필요성 | 구체적인 적용 법령·조문·의무 대상 판정, 남길 최소 필드 |
| 기한 | 기산일, 법정 기간, 항목별 실제 만료일, 삭제 담당자 |
| 결과 | 사용자에게 안내한 항목·근거·이의제기 방법, 만료 파기 일시/증빙 |

기부자별 영수증 발급명세의 해당 의무는 발급일+5년(전자영수증 예외 검토), 해당 공익법인등 장부·중요 증빙은 사업연도 종료+10년이다. 이를 일반 회원 자료 전체에 적용하지 않는다. 여러 의무가 중복되면 그 자료에 실제 적용되는 가장 늦은 만료일까지만 보존한다. 담당자가 매월 만료 목록을 확인해 지체 없이 파기하고 증빙을 남긴다.

## 자동 정리와 오류 처리

- 분당 최대 100건씩 처리 완료 신고 자료(완료 후 90일 경과)와 삭제 접수증(완료 후 30일 경과)을 정리한다. 분쟁/법정 보존 명령이 있는 증거는 신고 완료 전에 제한 보관소로 옮기고 만료일을 관리한다. 미처리 신고는 자동 만료하지 않지만 필요성은 매일 검토한다.
- 삭제 요청은 완료 전에는 자동으로 버리지 않는다. 기한 경과 요청도 운영자 목록에 남는다. 작업 중 오류를 감추거나 기한을 미루기 위해 요청을 재생성하지 않는다.
- outbox `FAILED`/자격증명 누락: 실제 공급자 철회 문제를 해결한 후 기존 worker의 재시도 필드/상태를 서버 관리자가 검토한다. 성공 상태를 수동으로 꾸미거나 암호화 토큰을 먼저 지우지 않는다. 지원 불가 계정의 실제 철회 대안은 별도 구현·검증이 필요하다.
- 삭제 작업 중 장애: 요청은 `processing`에 남겨 재개한다. 복원으로 삭제 전 자료를 재노출하지 않는다. 진단 로그에 개인 데이터/확인번호를 넣지 않는다.
- 요청 API 성공 뒤 네트워크가 끊겨도 앱이 미리 Keychain에 저장한 확인번호로 상태를 재조회한다. 기기 분실/확인번호 분실은 개인정보 담당자가 본인 확인 후 별도로 대응한다. 앱 재설치는 완료 통지를 위한 필수 단계가 아니다.

## 검증 증거와 미해결 사항

로컬 MariaDB 10.1.38의 가상 계정으로 접수, 중복, 권한 제거, 상태만 변경한 경우 차단, 실제 행 삭제, 공급자 증빙 누락 차단, 완료/회원 연결 제거, 보관 기한 정리를 검증했다. 공급자 실제 API, 운영 파일/백업/Sentry 삭제는 테스트하지 않았다.

출시 전 담당자가 제공/확인할 것: 공익법인등 해당 여부와 홈택스 전자 발급 여부, 해피나눔 전달 항목·계약, Sentry 설정/국외 이전 정보, 서버 백업 교체·선택 삭제 방식, 실제 운영자와 서버 관리자 접근 및 개별 통지 수단.
