## 전체 배포에서 함께 반영되는 변화

`deploy.sh`에서 `--only`를 생략하면 backend, frontend, admin 세 구성요소가 모두 선택된다.
이번 준비는 세 구성요소 전체, frontend `patch-mode=false`를 기준으로 했다.
선택한 구성요소의 최신 전체 산출물을 교체하며 탈퇴 관련 파일만 골라 배포하는 방식은 아니다.

## 배포 직후 자동으로 실행되는 작업

새 `AccountErasureJob`과 `PrivacyRetentionJob`은 서버 시작 직후 한 번, 이후 분마다 실행된다.
현재 코드에는 이 두 작업의 환경 변수 기반 비활성화 스위치가 없다.

- 자동 탈퇴는 **등록된 자동 처리 요청**을 대상으로 한다. 과거 `USR_STATUS=AAA`인 13명을 찾아 일괄 삭제하는 배치가 아니다. 현재 운영에는 새 요청 테이블 자체가 없다.
- 신규 요청이 접수되고 키·소셜 철회·기부 검토 등 조건이 충족되면 DB/파일 삭제가 진행될 수 있다. 외부 증거 확인이 지연되어도 DB 삭제 단계까지 진행할 수 있다.
- 보관 만료 작업은 처리 후 90일 지난 신고, 만료된 작업용 암호화 정보, 보존 종료일이 지난 분리 증빙, 완료 후 30일 지난 접수증/처리 상태를 정리한다. 이는 구현 조건이며 새로운 법적 보관 기간 판단이 아니다.
- 기존 데이터 정리 결재안의 DB 8행 삭제, PG 과거 9행 정리, 소유자 미확인 파일 정리를 실행하는 것은 아니다. 관련 CLI 도구도 배포 스크립트가 자동 실행하지 않는다.

따라서 이 후보 전체 배포는 테스트 계정에만 기능을 노출하는 배포가 아니다.
배포 결재와 운영 테스트 계정 삭제 결재는 구분하며, 준비 작업으로 자동 처리를 활성화하지 않는다.

## 별도 적용·확인이 필요한 설정

- `ACCOUNT_ERASURE_CONTEXT_KEY`, `DONATION_ARCHIVE_KEY`: 로컬 비공개 키 준비 완료, 운영 미설정. 배포 묶음에는 실제 값을 포함하지 않는다.
- `ACCOUNT_ERASURE_LEGACY_ROOT=/var/www/html/upload`: 확인한 실제 경로. 일반 파일 제공 경로 설정과 구분한다.
- 기부 자료의 검토 근거·거래별 보존 결정: 빈 값을 임의 승인하거나 보존 기간을 추정하지 않는다.
- `ACCOUNT_ERASURE_EXTERNAL_URL/TOKEN`: 운영 미설정이며 실제 외부 처리 연결도 미완료. 단순 더미 응답으로 완료시키지 않는다. Debug Agent 연결은 제거 결정에 따라 필요하지 않다.
- Sentry 관리자 조회: 현재 운영 조직은 `metanoia-lab`, 프로젝트 설정은 아직 `daeil-ios`/`daeil-android`다. 기존 토큰의 접근 범위를 확인하고 `daeil-ios-release`/`daeil-android-release`로 바꿔야 한다.
- `deploy.sh`는 이 환경 변수들을 자동 주입하지 않으며, 기존 사전 검사가 새 탈퇴 설정의 준비 완료까지 보장하지 않는다.

## 스크립트의 실제 운영 효과

파일 상단에 migration 수동 적용이라는 오래된 주석이 있지만, 실제 구현은 미적용 파일을 찾은 뒤
대화형 승인 또는 `APPLY_MIGRATIONS=1`이 있으면 **빌드 전에** migration을 적용한다.
따라서 준비를 위해 `deploy.sh`를 실행하지 않았다. 빌드 명령만 별도로 실행했다.

실제 전체 배포 시 backend/backfill을 교체하고 웹 자산은 `rsync --delete`로 이전 파일을 교체한다.
`/var/www/app`와 `/var/www/admin`에 대한 교체이며 회원 업로드 루트는 대상이 아니다.
backend를 재시작하고, Apache 설정이 달라졌을 때만 설정 교체·reload한다.
이번 후보의 Apache 설정 해시는 운영과 같아 현재 비교상 변경이 없다.

기존 작업폴더의 frontend/admin `node_modules`는 공유 symlink이므로 준비 중 `npm ci`를 실행하지 않았다.
현재 설치된 의존성으로 빌드·테스트했으며 lockfile 해시를 준비 자료에 기록한다.

## 준비 산출물과 검증

로컬 비공개 `~/.local/share/dflh-release/deployment-prep-20260907/`에 다음을 준비했다.

- Linux amd64 backend/backfill, `patch-mode=false` 사용자 웹, 관리자 웹의 실제 빌드 파일.
- 미적용 migration 8개와 각각의 SHA-256, 운영 기준/소스 변경 목록, 설정 검토 자료.
- 운영 backend/backfill·웹 자산의 로컬 복구용 사본. 운영에서 읽기만 했으며 배포 파일의 해시를 대조했다.
- 승인 상태가 `PREPARED_NOT_APPROVED_NOT_DEPLOYED`인 manifest와 검토용 배포 묶음.

일반 작업폴더에서 Go가 상위 작업공간의 VCS 정보를 기록하는 것을 발견하여,
고정 커밋을 별도 로컬 Git checkout으로 분리한 뒤 backend/backfill을 다시 빌드했다.
최종 바이너리의 `vcs.revision`과 `vcs.modified=false`를 검증한다.

backend 크로스빌드와 웹·관리자 TypeScript/Vite 빌드 통과.
웹 테스트 139개, 관리자 테스트 47개 통과. 앞선 탈퇴 검증 38개도 같은 후보 코드에서 통과했다.
웹 번들 크기 경고는 남아 있으나 빌드 오류는 없다. 준비 과정에서 앱 동작 코드는 바꾸지 않았다.

복구용 사본은 **애플리케이션 파일**이며 DB 데이터·스키마·삭제 결과를 되돌리는 백업이 아니다.

운영 계정 탈퇴 종단 검증과 실제 공급자 토큰 철회는 아직 수행하지 않았다.
