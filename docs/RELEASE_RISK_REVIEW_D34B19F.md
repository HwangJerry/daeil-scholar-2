## P1 — 쿼리·fragment가 붙은 공유 이미지 참조를 누락한다

- 위치: `backend/internal/model/erasure_file_path.go:15`, `:27`, `backend/internal/repository/account_erasure_file_references.go:58`.
- URL 분류 함수는 `?v=2`, `#preview`가 붙은 주소를 오류로 반환한다. 참조 검사에서는 이 오류를 무시한다.
- 예: A의 삭제 큐에 `/files/shared.jpg`가 있고 B의 글에 `/files/shared.jpg?v=2`가 남아 있어도 같은 파일의 참조로 인식하지 않는다.
- MariaDB 10.1.38 합성 자료로 실제 삭제 직전 검사 함수를 실행했다. 쿼리와 fragment 두 경우 모두 보호 assertion이 실패했고, 삭제 콜백이 호출되며 큐가 처리됐다.
- 별도 Go FileServer 검사에서 원본 주소와 쿼리가 붙은 주소가 동일한 합성 파일을 제공하는 것도 확인했다. 운영 파일을 삭제한 재현은 아니다.

삭제 후보 URL의 엄격한 검증과 기존 참조가 가리키는 파일의 식별을 분리해야 한다.
참조 비교에는 쿼리·fragment·허용된 호스트 별칭 등을 반영하고, 해석할 수 없는 참조를 조용히 무시해서는 안 된다.

## P1 — 중지 명령의 상태 확인 실패가 자동 삭제를 다시 켠다

- 위치: `deploy/remote_release.py:335`–`:347`.
- `--pause-erasure`도 활성화와 같은 예외 복구 분기를 사용한다.
- 중지 설정을 쓴 뒤 API/DB 건강 상태 확인이 실패하면, 기존 설정을 복원하고 백엔드를 다시 시작한다.
- 기존 설정이 `true`였다면 중지를 요청했는데 자동 삭제·만료 정리가 다시 실행될 수 있다.
- 임시 설정 파일과 모의 systemctl을 사용해 DB 장애를 주입했다. 중지 함수가 예외를 반환한 뒤 세 설정이 모두 `true`로 복구되고 두 번째 재시작이 호출됨을 재현했다.

중지 실패는 중지 상태를 유지하도록 처리해야 한다. 중지와 활성화의 실패 복구를 분리하고,
서버가 비정상 상태여도 중지 설정을 적용할 수 있어야 한다. 실행 상태를 확인할 수 없으면 확인 실패를 보고하되 자동 재활성화하지 않는다.

## P2 — 마지막 파일 검사에서 작성자 번호 0인 공용 게시글을 제외한다

- 위치: `backend/internal/repository/account_erasure_file_references.go:31`, `:99`.
- DB 삭제 후 검사에서는 `user=0`을 넘기는데 SQL은 그대로 `WHERE USR_SEQ<>0`이 된다.
- 따라서 마지막 검사에서 모든 남은 게시글을 확인한다는 의도와 달리 작성자 0의 공용 글은 빠진다.
- 삭제 큐 등록 뒤 작성자 0의 글이 파일을 참조하는 상태를 합성 DB에 만들었다. 삭제 콜백이 호출되는 것을 재현했다.
- 처음부터 작성자 0의 일반 URL 참조가 있었다면 큐 생성 단계의 `user=42` 검사에서는 차단될 수 있다. 이 발견은 마지막 재검사에서의 누락을 가리킨다.

특정 사용자를 제외하는 검사와 아무도 제외하지 않는 검사를 명시적으로 분리해야 한다.
